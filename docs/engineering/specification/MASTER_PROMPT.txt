# 13. ANDROID EXECUTION MODEL

Do not install GCC/JDK/Python simply to pretend the Android device is equivalent to Windows.

Preferred architecture:

Shared task specification
→ deterministic serialized payload
→ portable worker runtime
→ Android native execution
→ validated result.

Compiler logic

Worker transport
separate from
Platform execution.

# 5. COMPILER ENGINE: C, PYTHON, AND JAVA

Maintain genuinely separate language pipelines. They may share orchestration and artifact infrastructure, but language-specific parsing, validation, compilation, diagnostics, and output must remain appropriate to each language.

## 5.1 C pipeline

Implement and verify the existing C compiler pipeline.

Where supported by the current compiler architecture, it must include:

1. Source ingestion.
2. Lexical analysis.
3. Parsing.
4. Syntax diagnostics.
5. Semantic checks.
6. Intermediate representation.
7. Optimization passes.
8. Optimization result verification.
9. Code generation.
10. Native compilation using a discovered and validated toolchain.
11. Controlled execution where the job requests execution and the security policy permits it.
12. Artifact generation.
13. Build reporting.

Document the actual supported C language subset. Do not silently label unsupported language constructs as supported ISO C.

The pipeline must provide useful source-positioned errors and warnings wherever the underlying stages can produce them.

Optimization must preserve program semantics for the supported language subset. An optimization must not be accepted merely because it reduces the apparent number of instructions.

Implement differential or equivalence-oriented testing for supported transformations. Where formal equivalence cannot be proven, document the verification strategy and limitations.

Use genuine GCC or another explicitly supported native compiler for native executable generation. Discover toolchain locations safely and allow configuration when multiple toolchains exist.

Never invent a native executable by renaming source code or writing a dummy file.

## 5.2 Python pipeline

Implement and verify a real Python source pipeline.

Required behavior:

- Source validation.
- Syntax diagnostics.
- Source-positioned errors where available.
- Supported parsing and AST analysis.
- Documented optimization passes.
- Safe, bounded compilation or execution when requested.
- Real `.py` source artifact.
- Additional bytecode or compiled artifacts only where genuinely generated.
- Accurate build report.
- Clear separation between source transformation, bytecode generation, and actual program execution.

Use the configured CPython toolchain when required by the implementation. Do not claim that producing a Python source file is equivalent to creating a native executable.

Any optimization must preserve semantics for the supported subset and be tested against representative inputs.

## 5.3 Java pipeline

Implement and verify a genuine Java pipeline.

Required behavior:

- Source validation.
- Java compiler diagnostics.
- Supported parsing and analysis.
- Optimization stages where actually implemented.
- Real compilation using a compatible JDK.
- Genuine `.java` source.
- Genuine `.class` files when compilation succeeds.
- A runnable JAR only when it is correctly assembled and contains the required runtime entry point and dependencies.
- Accurate build and execution reporting.

Do not create a fake `.jar`, `.class`, or executable artifact when compilation fails.

Detect the installed Java toolchain and its version. Avoid hardcoding a particular patch release in tests.

If a task requires a specific Java capability, verify it before scheduling the task to a worker.

## 5.4 Cross-language behavior

Each language must have:

- An independent validation path.
- An explicit capability definition.
- Language-appropriate compiler stages.
- Language-specific error handling.
- Correct artifact extensions and metadata.
- Accurate timing and execution status.
- Language-specific tests.
- Consistent user-facing job and report formats.

The frontend must not accept arbitrary source text, silently switch compilers, or report a language as supported merely because the user selected it.

## 5.5 Artifact and report integrity

For each artifact, record relevant metadata such as:

- Artifact identifier.
- Owning user and job.
- Language.
- Artifact type.
- File size.
- Cryptographic digest.
- Creation time.
- Actual generation status.
- Retention or expiration information where applicable.

Verify the file digest when retrieving or validating stored artifacts.

The build report must include the requested language, job ID, relevant compiler stages, outcome, diagnostics, verified artifact list, actual timings, and meaningful failure information.

Never include internal worker IDs, private IP addresses, authentication credentials, raw secrets, private scheduler details, or unnecessary internal architecture information in user-facing reports.

Administrative diagnostics may expose appropriately authorized operational information, but secrets must remain redacted.

# 6. DISTRIBUTED COMPUTING AND SCHEDULING

GRID-X must implement a genuine distributed execution model.

The coordinator must own authoritative task state. Workers must never be allowed to declare their own results globally successful without coordinator validation.

## 6.1 Worker identity and enrollment

Each worker must have:

- A stable worker identity.
- An associated network or tenant.
- A registered platform type.
- A protocol version.
- A set of verified or declared capabilities.
- A lifecycle state.
- A last-heartbeat timestamp.
- Resource contribution settings.
- Enrollment and revocation state.
- Relevant diagnostic information.

Worker IDs must remain stable across restarts and reconnections when the same enrolled installation is being resumed.

Do not regenerate or renumber all workers when a worker disconnects.

Use distinct identifiers for users, networks, workers, jobs, tasks, task attempts, artifacts, and enrollment invitations.

Do not expose a long-lived administrative secret as a general worker enrollment credential.

## 6.2 Enrollment and consent

Implement an explicit, controlled enrollment workflow.

1. An authorized user creates or requests an enrollment invitation.
2. The system issues a high-entropy, time-limited, single-use token or another suitably protected invitation mechanism.
3. The user shares the invitation link or code with the intended contributor.
4. The recipient opens a dedicated enrollment page or native application flow.
5. GRID-X clearly explains the resource contribution being requested.
6. The contributor explicitly consents.
7. The server validates the invitation and its network ownership.
8. The worker completes authenticated registration.
9. The invitation becomes unusable for a second enrollment.
10. The user can revoke the worker later.

Enrollment invitations must be protected against replay, brute force, unauthorized network joining, accidental disclosure, and use after expiry.

Do not automatically execute computation merely because someone opened a shared link.

Browser consent must be separate from Windows and Android native enrollment. Browser permission does not authorize native installation, and native enrollment does not imply permission to execute arbitrary workloads.

## 6.3 Shared worker protocol

Create or complete a versioned protocol with explicit compatibility rules.

At minimum, define:

- Protocol version.
- Message type.
- Message identifier.
- Worker identity.
- Task identity where applicable.
- Attempt identity where applicable.
- Correlation identifier.
- Timestamp or deadline information where appropriate.
- Validated payload schema.
- Error format.
- Authentication and authorization requirements.

Reject malformed, unsupported, stale, or unauthorized messages.

Implement a clear version-negotiation and compatibility policy. A newer worker must not silently send unsupported message structures to an older coordinator.

Document backward-compatibility expectations and protocol upgrade behavior.

## 6.4 Scheduling

Build scheduling around actual worker capabilities and resource availability.

Account for:

- Language and task capabilities.
- Operating system and architecture.
- Toolchain availability and compatible versions.
- Worker connection state.
- Recent heartbeat.
- Resource contribution limits.
- CPU and memory budgets.
- Task deadlines.
- Estimated task cost where meaningful.
- Worker reliability.
- Retry history.
- Network ownership.
- Task affinity where required.
- Worker platform restrictions.
- Privacy and security restrictions.
- Whether a task is safe and useful to distribute.

Do not distribute a task to a worker merely because it is connected.

The scheduler must be deterministic enough to test and explain. Keep policy decisions separate from transport code.

If no eligible worker is available, report the actual condition and follow an explicit policy:

- Run a compatible local stage where permitted.
- Wait for eligible workers when configured.
- Offer a local fallback when supported.
- Fail with a useful reason when the operation cannot proceed.

Never silently claim distributed execution when everything ran locally.

## 6.5 Leases, timeouts, retries, and recovery

Implement robust task lifecycle management.

- Task offer.
- Acceptance or rejection.
- Lease expiration.
- Heartbeat timeout.
- Progress updates.
- Completion.
- Failure.
- Cancellation.
- Retry.
- Reassignment.
- Stale-result rejection.
- Coordinator restart recovery.
- Worker restart recovery.
- Job cancellation propagation.

Use idempotent operations where repeated requests are possible.

Persist sufficient state to recover after coordinator restarts. A task must not be treated as complete solely because a worker sent a completion message before the result was durably stored and validated.

Prevent multiple attempts from corrupting job state. Define how duplicate results are handled.

Use bounded retries and exponential backoff with jitter where appropriate. Prevent infinite retry loops.

Ensure cancelled jobs do not continue indefinitely consuming worker resources.

## 6.6 Distributed correctness and result verification

Implement result verification appropriate to each task type.

- Validate schema and payload size.
- Validate task and attempt identity.
- Validate worker authorization.
- Reject stale or duplicate attempts where inappropriate.
- Validate output digests.
- Validate artifact ownership.
- Verify deterministic transformations against coordinator-known expectations when possible.
- Use independent recomputation, reference outputs, or redundant execution for selected high-risk operations where practical.
- Distinguish structural validity from semantic correctness.
- Record verification status and the reason for rejection.

A checksum proves byte integrity, not that a computation is correct. A matching result from two workers is evidence of agreement, not proof against coordinated malicious behavior.

Do not claim Byzantine fault tolerance, cryptographic proof of computation, or mathematical equivalence unless a corresponding mechanism has actually been implemented and tested.

Implement practical correctness checks appropriate to the project, and document their limits.

## 6.7 Fault tolerance

Test and handle:

- Worker disconnection during execution.
- Worker process termination.
- Android application backgrounding or process termination.
- Browser tab closure.
- Coordinator restart.
- MySQL interruption.
- Slow worker responses.
- Invalid worker payloads.
- Expired task leases.
- Duplicate completion messages.
- Network interruptions.
- Artifact storage failures.
- Partial job failures.

The product must recover predictably without silently corrupting persistent state.

Where containers or other isolation facilities are available, use them according to a documented security design.

Do not claim that an untrusted native executable is securely sandboxed merely because it runs in a temporary directory.

For Windows, Android, and browser workers, define different execution policies where the operating systems provide different guarantees.

Reject tasks that cannot be executed within the worker's documented security boundary.

If full isolation cannot be established on a given machine, disable the unsafe workload type or clearly restrict its use. Do not conceal the limitation.

## 12.4 Protocol and result security

Validate every inbound message and every uploaded result.

Enforce payload size limits, message schemas, identity checks, authorization, protocol versions, task deadlines, replay resistance, and artifact ownership.

Prevent unauthorized workers from joining networks, claiming tasks, submitting results for other workers, or downloading unrelated artifacts.

Do not trust worker-supplied resource metrics or correctness claims without appropriate validation.

- Request and upload limits.
- Error information disclosure.

Correct overly permissive origin and proxy configurations identified by the audit.
